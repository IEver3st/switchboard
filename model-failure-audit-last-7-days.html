Operating rules:

1. Investigate before changing anything.
   - Read the effective AGENTS.md and relevant architecture, validation, and performance docs.
   - Inspect git status and treat unrelated or untracked work as user-owned.
   - Read the relevant shared contract, controller or service, state owner, and existing UI primitive.
   - Reproduce the current behavior and identify the owning root cause. Do not patch only the visible symptom.

2. Do the work, not just the plan.
   - After the audit, implement every safe in-scope correction yourself.
   - Continue through integration, regression repair, validation, and a second audit.
   - Do not stop midway to ask whether to continue when the next action is already within scope.
   - If one path is blocked, continue independent in-scope work and report the exact blocker and evidence.

3. Preserve architecture and real state ownership.
   - Reuse canonical contracts, typed boundaries, shared services, settings, and repository primitives.
   - Do not create renderer-only success, duplicate stores, parallel abstractions, or privileged shortcuts.
   - Preserve unrelated dirty changes. Do not reset, clean, overwrite, or silently include them.

4. Enforce product truth.
   - Every visible control must map to a supported capability and a real state transition.
   - Do not invent hardware writes, system-wide effects, telemetry, device state, submissions, or success.
   - Distinguish requested or preview state from pending, acknowledged, confirmed, unavailable, unsupported, and failed state.
   - A transport ACK, fixture, mock, or local React update is not readback or physical confirmation.
   - On failure, retain the last confirmed state or visibly explain the unavailable state. Never leave a convincing false success.

5. Treat UI work as an inspect-and-iterate task.
   - Inspect the exact changed route and all supplied reference images before implementation.
   - Match the intended information hierarchy, density, alignment, spacing, asset variant, control semantics, and interaction behavior.
   - Use the repository's existing shadcn/Radix or product primitives when requested. Preserve the actual underlying behavior.
   - Avoid generic SaaS composition, card soup, nested cards, pills, gradients, glow, glass, decorative icon boxes, excessive helper text, routine shadows, and developer details in the consumer UI.
   - Do not blindly clone another product. Use it as a quality and interaction reference while keeping this product's tokens, controls, copy, and capability model.
   - Keep routine controls and current state visible. Put low-level identifiers and protocol details in diagnostics only.
   - Preserve semantic controls, accessible names, visible focus, keyboard order, contrast, reduced-motion behavior, and Electron no-drag behavior where applicable.

6. Verify responsive and visual closure.
   - Render the exact changed screen at the required sizes. If none are supplied, check 1080x720, 1420x900, and 1920x1080 for desktop UI, plus a narrow layout when supported.
   - Check loading, empty, disconnected, unavailable, disabled, error, pending, success, focus, overflow, long-content, and reduced-motion states that apply.
   - Exercise every changed control and confirm canonical state after refresh, restart, or round trip when applicable.
   - Compare the result to the references again. Fix geometry, assets, hierarchy, and density mismatches before stopping.

7. Match proof to the claim.
   - Keep these evidence levels separate: source inspection, deterministic test, static browser or DOM render, native Electron, packaged application, live game/runtime, external confirmation, and physical hardware.
   - Run the repository's actual applicable checks. Do not claim a lint, test, package, runtime, or hardware result that did not run.
   - Build or regenerate tracked/generated output when the repository requires it, and fully restart processes when preload, native host, or packaged code can be stale.
   - Add targeted regression coverage for the root cause. Do not add meaningless tests only to raise a count.

8. Use a completion loop.
   Reproduce -> trace root cause -> implement -> run focused checks -> run full applicable gates -> inspect the real UI/runtime -> exercise state and failure paths -> fix regressions -> repeat the affected checks -> audit the result again.

Completion is allowed only when:
   - the requested behavior works through the real owning path;
   - the UI matches the requested visual and interaction intent at target sizes;
   - refresh, restart, persistence, error, and unavailable behavior agree with canonical state;
   - unrelated work remains preserved;
   - evidence supports every success claim;
   - any remaining physical, live, permission, or external blocker is named precisely without being presented as complete.

Final response format:
   - Outcome: what is now true.
   - Changed: the important files or systems changed.
   - Verified: exact commands, routes, viewport sizes, interactions, round trips, and evidence levels.
   - Remaining limits: only genuine external, physical, live, or permission blockers.

Keep the final report concise. Do not hide incomplete work behind a long summary.
