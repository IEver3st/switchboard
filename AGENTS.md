# AGENTS.md

## Mission

Build Switchboard as a low-overhead, modular Windows hardware, audio-routing, and game-capture utility. It is a desktop control surface, not a website, a generic dashboard, or another monolithic peripheral suite.

## Sources of truth

- Use Bun for JavaScript package and script work.
- Treat `src/shared/contracts.ts` as the canonical renderer/main/host contract and Electron main as the owner of persisted state. Zustand is a renderer projection, not a second source of truth.
- Read `ARCHITECTURE.md` for subsystem boundaries, `README.md` for confirmed prototype claims, and `PERFORMANCE.md` before changing resource budgets or long-lived work.
- Read the relevant contract, controller, and shared primitive before changing a page. Extend an existing pattern when one already expresses the concept.
- `preview/standalone.html` is generated by `bun run preview:static`; do not hand-edit it.
- Treat unrelated working-tree changes as user-owned. Do not reset, clean, overwrite, or include them in the task.

## Architecture invariants

1. The renderer never receives Node access.
2. Preload exposes narrow typed operations, never generic `ipc.send`, arbitrary filesystem access, or arbitrary process execution.
3. Validate untrusted module, package, and IPC input with Zod at the boundary.
4. Device-family and vendor-protocol code does not belong in the core renderer or core orchestration layer.
5. Realtime audio or video buffers never pass through Electron IPC and realtime work is not moved into Electron main for convenience.
6. Disabled engines retain no process, timer, device handle, subscription, or encoder session.
7. Realtime callbacks remain allocation-free: no LINQ, logging, locks, async work, object creation, or UI calls.
8. Long-lived resources have deterministic, idempotent disposal; shutdown and crash recovery are safe to repeat.
9. The virtual audio driver contains transport only: no DSP, profiles, networking, updating, or product policy.
10. One canonical contract exists for modules, devices, audio buses, capture configuration, diagnostics, and engine status. Do not create renderer-only duplicates.
11. Prefer event-driven device changes. Any polling must document its interval, reason, and stop condition.
12. Do not add a dependency for a helper or primitive that can be implemented safely in a few lines.
13. Windows realtime hosts use C# / .NET 10. Use NAudio unless profiling or missing API coverage proves a direct COM path necessary.
14. Capture is FFmpeg-first. Replace any portion with Vortice or Windows.Graphics.Capture only when a measured limitation requires it.
15. Use C++/WDK only for virtual audio endpoints; keep product policy and DSP in user mode.

## Product-truth invariants

- A visible control must correspond to a supported capability and a real state transition through the canonical contract. A local React-state change is not feature completion.
- Do not add fake search, fake analytics, fabricated telemetry, simulated capability controls, or UI-deep audio/capture features. Prototype and unavailable behavior must be identified beside the affected control.
- Unsupported capabilities are absent, or visibly unavailable with a useful reason when their presence helps explain the system. Never render a convincing but inert control.
- Keep ordinary product state in the primary interface and low-level identifiers such as VID/PID, HID paths, protocol details, and internal IDs in a diagnostics-only context.
- Do not describe virtual audio routing, production game capture, or hardware writes as complete until validated on the relevant Windows hardware and host path.

## Renderer invariants

- Extend Switchboard's continuous-console design language. Do not restyle a page as a generic SaaS dashboard, marketing hero, component-library demo, gaming overlay, or hyper-futuristic control room.
- Gradients, glow, glassmorphism, neon/chroma decoration, decorative blur, particles, tilt, floating animation, decorative waveforms, and ambient visualizers are prohibited.
- Do not use pill-shaped text containers, giant radii, card grids, nested cards, floating bubbles, decorative icon boxes, excessive borders, or routine shadows. Surfaces must communicate a real functional boundary.
- Keep primary controls, current state, recovery actions, connected hardware, the complete audio signal chain, mixer meters/faders, and EQ visibly prominent. Do not hide routine work in modals, accordions, deep tabs, or repeated disclosure clicks.
- Use real product imagery and the correct known hardware variant. Do not fabricate, recolor, or replace an available render with a generic placeholder.
- Use purpose-built controls: switches for booleans, exposed choices for small discrete sets, faders/knobs/sliders for meaningful continuous adjustment, and specialized graphs only for real specialized data.
- Preserve consistent typography, alignment, spacing, control sizing, state styling, and shared interaction patterns across pages. A new page must look designed by the same product team.
- The minimum supported window is 1080 x 720; the standard review window is 1420 x 900; also inspect 1920 x 1080. At 1080 x 720 there must be no page-level horizontal overflow and no mandatory scroll before critical status or routine controls.
- In an Electron window or game overlay, only intended controls may receive pointer input. Never make an entire transparent or full-screen layer interactive by accident.

## Coding rules

- Use small services and explicit interfaces; avoid generic service locators and speculative plugin frameworks.
- Preserve process isolation and state ownership when polishing UI. Styling work does not authorize mock state, duplicate stores, or privileged renderer behavior.
- Keep accessibility intact: semantic controls, accessible names, visible focus, logical keyboard order, sufficient contrast, reduced motion, and `no-drag` on interactive elements inside Electron drag regions.
- Do not copy another product pixel-for-pixel. Reuse useful information architecture while keeping Switchboard's own tokens, controls, copy, and capability model.

## Validation before completion

Run, or explain why the environment cannot run, all applicable checks:

```powershell
bun run check
bun run check:source
bun run build
dotnet build .\engines\capture-host\Capture.Host.csproj
dotnet build .\engines\audio-host\Audio.Host.csproj
```

For renderer work, inspect the exact changed route in Electron at 1080 x 720, 1420 x 900, and 1920 x 1080. Exercise every changed control and verify canonical state after a refresh or round trip; inspect loading, empty, unavailable, disabled, error, focus, overflow, and reduced-motion states that apply. Static browser or DOM checks are supporting evidence, not proof of native Electron behavior.

For affected Windows behavior, also test the relevant lifecycle: repeated engine start/stop, killed-host recovery, renderer release on close-to-tray, device disconnect/reconnect, default endpoint changes, replay ring-wrap saves, and long-running memory/handle behavior. State clearly when physical hardware or soak validation remains external.

## Completion standard

A task is not complete because the UI looks acceptable once. It is complete when information architecture, capability truth, state ownership, failure handling, cleanup, persistence, security boundaries, responsive behavior, accessibility, and applicable runtime evidence all agree with the change.
